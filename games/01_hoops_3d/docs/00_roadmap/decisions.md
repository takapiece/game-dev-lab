### [ADR-001] 初期プロトタイプに Web 3D (Three.js) を採用

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * 『NBA 2K Mobile』のようなゲームを作る際、Unity や Unreal Engine を使う選択肢もありますが、初学者にとってはツールのインストール、巨大なプロジェクトファイル、ビルド待ち時間などの心理的・技術的ハードルが存在しました。
* **決定理由 (Decision):**
  * ブラウザだけで即座に起動し、コードを1行書き換えるとホットリロード（Vite）で画面が即時変化するため、生徒の学習フィードバック速度が最大化される。
  * Three.js を使うことで、3Dの基本概念（メッシュ、ジオメトリ、マテリアル、カメラ、ライト）を生のコードで理解できる。
* **結果 (Consequences):**
  * ネイティブアプリ専用の重いシェーダーは使えないが、PC・スマホ（iPhone/Android）両方のブラウザで即座に動作する軽量なプロトタイプを最短で作成できた。

### [ADR-002] 外部画像・音源を使わず「コードによる動的生成」を採用

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * 通常のゲームではテクスチャ画像（png/jpg）や効果音（mp3/wav）をサーバーからダウンロードしますが、パスの参照エラーやロード遅延、CORSエラーの原因になりやすいという課題がありました。
* **決定理由 (Decision):**
  * **コートテクスチャ:** HTML5 Canvas API で木目や白線をプログラム描画してテクスチャ化。
  * **効果音:** Web Audio API のオシレーター（発振器）とフィルターで音をリアルタイム合成。
* **結果 (Consequences):**
  * 外部アセットへの依存がゼロになり、ロード時間なし・エラーなしで確実に動く堅牢なゲーム基盤となった。
  * 生徒が「音や画像がどのように数値やコードで表現されるか」を学べる教材となった。

### [ADR-003] 最新の Antigravity 仕様 (`.agents/`, `GEMINI.md`) への準拠

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * プロジェクトのナレッジを AI と共有する際、古い非公式フォルダ構成だと AI がコンテキストを正しく認識できない、またはトークンを無駄に消費する問題がありました。
* **決定理由 (Decision):**
  * ルートに `GEMINI.md` を配置し、AI に生徒指導ルールを常駐化。
  * `.agents/skills/` によるオンデマンド読込を採用し、AI のトークン消費を最小化。
* **結果 (Consequences):**
  * 毎回の開発セッションで、AI が一貫したフォーマット（教育的解説＋エラーログ記録）を破綻なく継続できるようになった。

### [ADR-004] グリーンリリース・シュートメーター機構の採用

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * 単なる「シュートボタンを押したら一定確率で入る」ゲームだとプレイヤーの腕前（スキル）が反映されず、ゲームとしての面白さが薄いという課題がありました。
* **決定理由 (Decision):**
  * プレイヤーのタイミング技術がダイレクトに反映される「長押しして緑のタイミングで離すと100%入る（Green Light）」メーターを採用。
* **結果 (Consequences):**
  * タイミングに応じた爽快感と中毒性の高いコアゲームプレイが実現した。

### [ADR-005] 著作権配慮による「HOOPS 3D」への改名 & マルチゲーム拡張構成

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * 商標・著作権（NBA / 2K）に配慮したオリジナル名称への変更と、今後複数のゲームを開発していく拡張性が必要となった。
* **決定理由 (Decision):**
  * ゲームタイトルを **『HOOPS 3D』** に統一。
  * `games/<game_name>/` 配下に各ゲームを独立して格納するマルチプロジェクト構成を採用。
* **結果 (Consequences):**
  * 権利面でクリーンになり、第2弾・第3弾のゲームも同じ教材リポジトリ内で安全かつ独立して開発可能になった。

### [ADR-006] Windows / Mac 完全互換のための全ドキュメント相対パス化

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * Google Drive や Git を介して Windows（`D:\`）と Mac（`/Users/`）を行き来する際、絶対パスリンクが切れる問題を防ぐ必要があった。
* **決定理由 (Decision):**
  * プロジェクト内のすべてのリンク・インポートを標準相対パス（`./...`, `../...`）で記述することを必須規約とした。
* **結果 (Consequences):**
  * OSに依存せず、どの端末で開いてもリンク切れなく教材ドキュメントを閲覧できるようになった。

### [ADR-007] Git バージョン管理とクロスプラットフォーム設定（`.gitignore` / `.gitattributes`）の導入

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * Google Drive や複数OS（Windows / Mac）間での共有において、`node_modules` や `dist` などの巨大ファイル群、OS固有の隠しファイル（`desktop.ini`, `.DS_Store`）、改行コードの差異（CRLF / LF）が同期エラーや Git 差分爆発を引き起こすリスクがあった。
* **決定理由 (Decision):**
  * リポジトリルートに包括的な `.gitignore` を配置し、ビルド生成物やOS固有ファイルを確実に除外。
  * `.gitattributes` を導入してテキストファイルの改行コードを LF に統一 (`* text=auto eol=lf`)。
* **結果 (Consequences):**
  * クリーンで軽量なリポジトリ状態が維持され、生徒がどの開発環境（Win/Mac/Linux）からでもトラブルなくコードを取得・共同開発できるようになった。

### [ADR-008] 1v1 AIディフェンス思考ルーチンおよび幾何学的コンテスト・ブロック判定の導入

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * 単独のシュート練習から、バスケットボール特有の「マークを外す駆け引き（1v1）」のゲームプレイへ進化させる必要があった。
* **決定理由 (Decision):**
  * **AIポジショニング:** ベクトルの内分点を用いて「ボールマンとゴールの間」に回り込むステートマシン（GUARD, CONTEST, REBOUND）を設計。
  * **コンテスト計算:** 距離・角度（内積）・手の高さを乗算した幾何学的妨害度（0〜100%）を算出し、シュートの成功率と弾道ブレに反映。
  * **近接ブロック:** 至近距離かつジャンプの頂点付近で叩き落とす物理演出と Web Audio API による専用スラップ音を実装。
* **結果 (Consequences):**
  * ダッシュや切り返しでマークを振り切る戦術的深みが生まれ、ゲームの面白さが格段に向上した。
  * 生徒にとって「ベクトルや内積がゲームロジックでどのように役立つか」を学べる優れた教材となった。

### [ADR-009] マルチエントリー・独立フェーズスナップショット構成（`phases/` + ポータル画面）の採用

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * プログラミング教室のカリキュラムとして「過去のフェーズ（Phase 1など）のコードや動作」を生徒がいつでも体験・比較できるようにする必要があった。
  * 最新コード内にフラグ分岐（`if (phase === 1)`）を残す手法では、将来の大きな構造変化（物理エンジン導入やモデル差し替え等）に耐えられず、レガシー負債化する懸念があった。
* **決定理由 (Decision):**
  * 各フェーズ完了時のコード一式を `phases/phase_XX/` 配下に完全独立したスタンドアロン構成でスナップショット保存。
  * ルートに Vite マルチページ対応の「フェーズ選択ポータル画面（`index.html`）」を配置し、サーバー1台（`npm run dev`）で全フェーズをワンクリック起動可能にした。
* **結果 (Consequences):**
  * 将来どれほど大規模なアーキテクチャ刷新が行われても、過去の全フェーズが100%永久に壊れずに稼働し続ける堅牢な教材構造が完成した。
  * 生徒がフォルダ間の Diff（コード差分）を比較することで、各回の学習内容を直感的に把握できるようになった。

### [ADR-010] 学習用ダッシュボード（要件・コード・数学・AIプロンプト指導入門）の統合導入

* **ステータス:** 採用 (Accepted)
* **背景 (Context):**
  * ゲームを単に動かすだけでなく、生徒や講師が「各フェーズの仕様・ファイル構造・ソースコード・必要な数学/技術知識・AIへの指示出しのコツ」を1つの画面で包括的に学べる学習用インターフェースが必要となった。
* **決定理由 (Decision):**
  * `dashboard/` 配下に専用の学習ダッシュボードを構築。
  * フェーズ切り替えに連動して「概要」「コード閲覧（ファイルツリー）」「数学・前提知識」「AI指示ガイド（悪い例 vs 良い例）」「トラブル解決事例」を動的表示するタブUIを実装。
* **結果 (Consequences):**
  * プログラミング教室の授業でそのままプロジェクター投影・自習教材として使える高品質な学習ハブが整った。
  * 生徒が AI を使って開発する際の「具体的で精度の高いプロンプト作成スキル」を自然に身につけられるようになった。

## [ADR-011] 2v1 パス＆コントローラースイッチ機構の設計
* **ステータス:** 承認済み (Accepted) / 2026-08-30
* **背景 (Context):**
  * 1v1 からチームオフェンスへ拡張するにあたり、複数の味方プレイヤーをどう操作し、ボールの移動とプレイヤーの役割（操作対象 vs AI自律移動）をどう両立させるかが課題となった。
* **決定理由 (Decision):**
  * `Player` クラスに `isActive` と `hasBall` のフラグを持たせ、操作中（Active）はユーザー入力、非操作中（Inactive）はオフボール・スペーシングAIとして自律移動させる設計を採用。
  * パス到達時に `activePlayer` と `inactivePlayer` のポインタ参照を安全にスワップすることで、操作権限とカメラ追従を瞬時に移行。
* **結果 (Consequences):**
  * 2人以上のチームプレイでもコードが肥大化せず、統一された `Player` クラスで拡張可能なアーキテクチャが実現した。

## [ADR-012] 24秒ショットクロックとバイオレーション演出の実装
* **ステータス:** 承認済み (Accepted) / 2026-08-30
* **背景 (Context):**
  * バスケットボールゲームとしての緊張感と戦術性を高めるため、攻撃時間制限ルールの導入が必要となった。
* **決定理由 (Decision):**
  * 毎フレームの `delta` 時間をポゼッション保持中に減算するデジタルタイマーを実装。
  * 残り5秒以下で赤色警告表示、0秒到達時に Web Audio API によるスタジアムホーンブザー（`playBuzzer`）を鳴らしターンオーバー・リセットを行う。
* **結果 (Consequences):**
  * 「制限時間内にパスでズレを作ってシュートを打つ」という本物のバスケのゲームサイクルが確立した。

## [ADR-013] データ駆動型（Data-Driven）選手カード＆ステータス設計
* **ステータス:** 承認済み (Accepted) / 2026-09-05
* **背景 (Context):**
  * 選手ごとの個性（3ptシューター、スピード特化、ディフェンス職人）を実装するにあたり、ハードコードではなく拡張性の高いアーキテクチャが必要となった。
* **決定理由 (Decision):**
  * `roster.js` に選手カードマスターデータを集約し、`threePt`, `speed`, `defense` の数値を元に、移動速度やシュートメーターの緑ゾーン許容誤差（tolerance）を動的計算する設計を採用。
* **結果 (Consequences):**
  * 生徒がコード本体を変更せず、設定値の追加・調整だけで新しい選手カードを自由に量産・カスタマイズできる教材構成となった。

## [ADR-014] 2v2 協調ディフェンスAIと ON-FIRE パーティクル演出
* **ステータス:** 承認済み (Accepted) / 2026-09-05
* **背景 (Context):**
  * 2人対2人のチーム対戦において、ディフェンス側がバラバラに動くのではなく、状況に応じたマンマークとゴール下へのヘルプカバー（ダブルチーム）を連携させる必要があった。
* **決定理由 (Decision):**
  * D1（ボールマン担当）と D2（オフボール・ヘルプ担当）に役割を分け、ボールマンがペイントエリア（3.8m以内）に侵入した際に D2 がゴール前へヘルプに入る協調ルーチンを実装。
  * 連続3回成功（Streak 3）で発動する ON-FIRE モードには、外部画像不要のプロシージャル炎パーティクルシステム（`FireEffect`）を採用。
* **結果 (Consequences):**
  * 「ヘルプを誘ってフリーの味方にパスする」という本格バスケ戦術と、NBA Jam風のド派手な覚醒爽快感が両立した。

## [ADR-015] レベルデザイン・ゲームバランス調整パネル（Tuning Panel）の導入
* **ステータス:** 承認済み (Accepted) / 2026-09-05
* **背景 (Context):**
  * プロトタイプ開発や教育現場において、ゲームの「手触り（ゲームフィール）」や「難易度」を検証する際、コードを書き換えてビルドし直すのは試行錯誤のコストが高かった。
  * 生徒が「数値をいじるとゲームがどう変わるか」を体感的に学ぶレベルデザインの実験場が必要だった。
* **決定理由 (Decision):**
  * `tuning.js` および `tuning_ui.js` を新設し、画面上の半透明スライダーパネルから、メーター幅、シュート許容時間、リング吸い込み磁力、ディフェンス妨害距離などをリアルタイムに調整できる仕組みを導入。
  * 初心者向けの「爽快・アーケード」、標準の「ノーマル」、高難易度の「NBAプロ」の3大プリセット切替と LocalStorage 保存をサポート。
* **結果 (Consequences):**
  * プレイ中にその場で数値を動かしながら最適なゲームバランス（レベルデザイン）を探索できるようになり、生徒がゲームプランナー／デザイナーの思考プロセスを直接体験できるようになった。
