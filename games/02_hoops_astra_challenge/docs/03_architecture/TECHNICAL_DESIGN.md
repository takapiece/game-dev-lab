版1.0 / 2026-09-20 / 設計案。サンプルコードの実行・検証済みを意味しない。

初版はGameシーンを一つにし、GameplayRootとEnvironmentRootを分ける。EnvironmentRootは現在の環境だけを有効にする。4環境の床モデルと光だけを切り替え、当たり判定の床・ゴールは共通コアに置く。Scene別のLightmap等が必要になった場合にのみ4Scene方式へ変更し、両方式を並行運用しない。

4WorldConfigに環境Prefab、初期位置、照明プリセット、守備倍率、表示名を置く。設定はScriptableObject等で保持するが、過剰な汎用フレームワークを先に作らない。

## 2. 責任分担

| コンポーネント例 | 責任 |
|---|---|
| PlayerController | 入力、移動、向き、操作禁止状態 |
| ShotController | チャージ、入力評価、投球予約、初速 |
| BallController | 球の状態、shotId、物理切替、寿命、復帰 |
| DribbleController | 保持中の見た目。飛行中は球に触れない |
| DefenderAI | 守備位置、反応、現在の守備圧 |
| BasketScore | リング通過判定、一投一得点 |
| GameManager | 現世界の成功数、クリア、結果・再開 |
| WorldManager | 環境差し替え、初期化、重複防止 |
| CameraDirector / GameUI | 視点・演出・表示。ゲーム判定を所有しない |

これは責務の目安であり、指定ファイル数を満たすための分割は不要。ただしGameManager一つへ入力・物理・AI・UIを全部詰め込まない。編集用の生成コードはEditorフォルダに分離し、実行ビルドへ含めない。

## 3. 人物の統合で先に検証すること

最初に1体だけインポートし、身長、正面、足元原点、Humanoidマッピング、待機・移動クリップを確認する。全パックを導入してから不具合を探さない。

移動はCharacterControllerまたは既存の使用許可されたコントローラーに一元化。Starter Assetsを使う場合はジャンプとSpaceの競合を除き、Input Systemとカメラの依存版を確認する。[S04][S18]

バスケ固有のボール保持・ドリブル・シュートは、ゲーム状態からアニメ状態を一方向に駆動する。Animation Eventは投球タイミングの通知に使えるが、同じイベントが二重に来てもshotIdと状態で拒否する。通知不発時の復帰を用意する。手に球を追従させる箇所とIK/ポーズ補正の更新順序を固定する。

## 4. 初速設計

投球の計画値として、発射位置p0、目標の球中心pT、重力の大きさg、最高点Hを使う。Hは両端の高さより上に置く。空気抵抗なし・一様重力を仮定した設計式は次の通り。

```text
vy = sqrt(2 * g * (H - p0.y))
t_up = vy / g
t_down = sqrt(2 * (H - pT.y) / g)
T = t_up + t_down
vx = (pT.x - p0.x) / T
vz = (pT.z - p0.z) / T
```

これは本書の設計式で、衝突後の着地や得点の保証ではない。g>0、H>max(p0.y,pT.y)、T>0、有限値を検査する。最初の検証ではlinearDampingを0にし、目標へ下降しながら達する軌道を作る。入力や守備による誤差は投球前の狙い点等へ与え、飛行中に球を毎フレーム追尾させない。

Unity6ではDynamicへ切替後にlinearVelocityを一度設定する。保持中のkinematic状態で速度を設定したり、毎物理ステップで理想速度を上書きしたりしない。実際に使うエディター版のAPIに合わせる。[S12][S13]

## 5. 衝突形状・スケール

球はSphereCollider。バックボードと床は単純なBoxCollider。リングは外観メッシュとは別に、少数のCapsule等を円状配置する複合静的コライダー、または動かさない非凸メッシュとして検証する。初版は細かなネットの物理を省く。

単一の凸コライダーで輪の穴を埋める、LineRendererに自動で衝突が付くと考える、球を非一様スケールにする、といった実装を避ける。

FixedUpdateで物理状態を扱い、入力は取り逃さない形で受け渡す。高速球には適切なCCDモードを検討し、処理負荷を測る。CCDは得点用Trigger通過の万能保証ではない。[S14][S19]

## 6. 得点の確定

有効なFlying状態のshotIdだけを対象とする。前後の物理位置pPrev、pNowから、球中心がリング面を下降横切りしたか調べる。横切り時刻の補間位置がリング内の有効半径にあり、まだ未採点であれば得点候補とする。

球の半径を考慮した有効半径は実寸と衝突形状に合わせ、見た目では入っていないのに加点する大きな許容値を置かない。上下Triggerは領域候補や状態の補助には使えるが、イベント順だけで決めない。

得点確定は一箇所だけで行い、先にshotIdを採点済みへ変更し、その後GameManagerへ通知する。Rでの再開始、世界変更、リセットでは旧shotIdを無効化する。

## 7. 状態遷移と競合防止

```text
Menu → Playing → StageClear → Transition → Playing → ... → Finished
                  ↑ 成功3本

Dribbling → Charging → ShotPending → Flying → Resolved → Resetting → Dribbling
```

Game状態がPlaying以外なら新規投球を受け付けない。一時停止は独立したフラグで管理し、入力・球・守備を止める。Escやフォーカス喪失でのチャージ取消、解除待ちを共通化する。

世界移行では入力停止→進行保存→旧環境除去または無効化→新環境設定→球・人物・UI・カメラ初期化→入力復帰、の順にする。非同期処理がある場合は完了通知を重複受理しない。

## 8. 短時間開発で切るもの

DOTS/ECS、学習型AI、ネットワーク同期、自作汎用アセット管理、大規模シェーダー、全世界ベイク、高精細ネット物理を先行導入しない。Cinemachineや連携ツールも、環境に存在するかを先に確認する。

Unityを開いたまま同一プロジェクトへ別エディターのbatchmodeビルドを重ねない。ビルド中のタイムアウトと失敗を区別し、ログ・終了コード・生成物の3点で判定する。エラーを握りつぶして合格ログを作らない。

## 9. 保存と将来の教材化

チェックポイントは実行ビルドだけでなく、対応するソース、Packages、ProjectSettings、.metaを固定する。Gitを使う場合は既存ルートを確認し、許可範囲のコミット/タグ等で識別する。Git未使用なら必要ファイルのアーカイブで代替する。

Library、Temp、Logs、Obj等は再生成物。GitignoreはDrive同期を制御しないため、作業場所・同期方針を別に確認する。新しいPCで同時に同じUnityプロジェクトを開かない。

Sceneの保存だけでは過去教材のコード状態は固定されない。教材配布は依存版と素材条件を固定したスナップショット単位で設計する。

## 2026-09-20｜G1近距離と公式ルールの反映

最短距離1.5mの拒否を撤廃。最大8.5mと無効状態ガードは維持する。HoopsActor.BallAnchorは近距離で保持中の位置を外側へ寄せ、手のIKと実際の発射位置に同じ座標を使う。飛行中はRigidbodyのみが位置を所有する。

ShotLedgerは下降して球中心がリング面内に入った後、中心がさらに球半径ぶん下の面を通過した時点で得点を確定。上向きの中心侵入→球全体の通過は違反として同じshotIdを無効にする。リセット時は両方向の途中状態も破棄する。HoopsBallはボードの裏向き接触法線とSupport/SupportArmへの接触を無得点終了にし、通常の自動復帰へ渡す。現コートではボードのローカル+Zが裏面。

公式規則とゲーム側で省略した項目はREVIEW_DECISIONSの第8節。全競技規則への準拠は主張しない。

## G2の簡易シュート動作と描画検証

HoopsActorはAnimatorの基本動作の後に骨のため・足位置維持・体の傾き・腕IKを適用。HoopsGameのPending進行に合わせて球を1.8mまで上げ、実際のLaunchと同時にフォロースルーを開始する。Pause中は追加骨変形も停止し、Restartでフォロースルーを解除する。飛行中の球へ骨の座標を適用しない。

HoopsVisualReviewは開発用引数`--g2-review`でのみ実行。通常ウィンドウで9場面と骨座標を保存し、短時間の30fps制限描画を計測する。人間入力の証拠とは区別。詳細はG2-02のVALIDATION.md。

## G2の方向別移動とドリブル（2026-09-20）

G1AssetCheck.EnsureLocomotionLoopsがModelImporterのクリップ設定へloopTime/loopPoseを保存し、再ビルドでも残す。旧Locomotion.controllerは固定版の互換のため保持し、現行シーンはLocomotionV2.controllerを使う。移動方向の2Dブレンドと前進時の歩行/走行ブレンドを組み合わせ、実移動量からSpeed・MoveX・MoveZを設定する。通常の移動は進行方向、チャージ中はゴール方向、守備は相手方向を向く。Root Motionは無効。

通常の脚運動はクリップをそのまま使い、しゃがみや構えの補正が必要なときだけ脚IKを適用する。移動速度は従来どおり4.5/6.2m毎秒。ドリブル周期は1.5～2.15回/秒、球中心は基本0.14～1.06m。手は低い球を床まで追わず腰付近へ戻す。Gather0.14秒、Pending0.16秒の補間後、従来と同じ最終位置から物理投球する。

HoopsMotionReviewは`--g2-motion`で起動する描画付きの自動振付。歩行/ジョグ/走行/守備を各4秒継続し、最初の2秒を除いた骨位置・ループ・方向・ドリブルを検査する。走行→照準→投球、リセット、Pauseも含む。足が動いていることと、接地中の滑りがゼロであることは別の評価とする。

### 遷移と実装順

```text
攻撃：準備 → 始動 → 移動 → 制動 → 準備
                     └→ 切り返し → 移動
      ドリブル → 構え・Gather → リリース → フォロースルー → 準備/移動
守備：基本姿勢 ↔ 横・後ろ移動
      基本姿勢 → 追走 → 接近・制動 → 基本姿勢
      基本姿勢 → シュートへの対応 → 基本姿勢
```

1. プレーヤー：M01～M04の基本姿勢・始動・停止・切り返しを整え、M07～M10の走行・ドリブル・投球へ接続する。M14の中断復帰も確認し、動くビルドと記録を残す。
2. 敵：プレーヤーの動作確認後、M05/M06の低い構えと守備移動、M11～M13の追走・接近制動・シュートへの対応を整える。敵にもM07/M14を適用する。
3. 両者を同一経路で連続描画し、短い入力や連続反転での破綻、接地、入力・得点の回帰を検証する。

ルートの位置は引き続きCharacterControllerだけが所有する。まず姿勢表現を改善し、移動速度4.5/6.2m/s、CPU速度2.55m/s・反応間隔0.20秒、投球待ち0.16秒は変えない。操作感に影響する慣性・制動距離の導入は別の設計判断にする。守備姿勢を変えるためにCPUの強さを上げない。

基本クリップ→始動/制動/守備の体の補正→必要な足・腕IKの順に整理する。体の沈み込みを複数の処理で足し続けず、そのフレームで一つの目標姿勢へ混ぜる。中断・初期化を最優先とし、投球動作と移動用の制動が同時に膝を曲げすぎないよう状態を分ける。短い入力や壁への接触で始動・制動を毎フレーム再発火させない。移動入力と実移動速度の両方を見て、準備姿勢からの短い蹴り出しを優先する。

確認手順と未実施の合否項目は[ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md)第10節。静止画一枚や「骨が動く」だけを自然さの合格にしない。

### G2-23 足元リング

G1Build.FootRingで外半径0.46m/内半径0.425mの64分割メッシュを生成し、共有Meshアセットとして保存。人物RootにMeshFilter/MeshRendererだけを付け、高さ0.045m・チーム色・影なしにする。中央の三角形と側面はない。Build-CheckpointはEditorコードも正本からTEMPへ同期する。

### G3 4世界と衣装

G3WorldBuildはEnvironmentRoot配下の4子を生成。HoopsWorlds.World配列に環境参照・床/ペイント材質・空色・環境光・主光源を保存する。実装は同一Street.unity内の直列化データであり、上のPrefab/ScriptableObject配置案そのものではない。物理床・ゴール・球・人物は共通。環境装飾にColliderは付けず、競技空間への障害物は追加しない。

HoopsGameはWorldIndexとcompletedAttemptsを保持。TourAttempts=前世界の確定試投+現在試投、TourMakes=WorldIndex×3+現在成功。NextWorldで確定して世界を進め、Restartは現在値だけを消す。Begin/ReturnToTitleは通算も消す。設定は別管理。HoopsCamera.ResetViewは一時非表示を復元してRendererキャッシュを破棄し、新環境の初回演出で再取得する。

HoopsOutfitは既存Rendererの材質スロットを識別し、4セットの保存Materialへ差し替える。頭の帯はHead骨に付けた自作メッシュ。ActorとAnimatorの実体は交換せず、既存の骨参照・IK・歩行を維持する。

### G3-05 音楽の状態同期

HoopsAudioがSE用と音楽用の2 AudioSourceを保持。streetMusicは保存済みAudioClipを参照し、AudioImporterはVorbis品質0.85/Streaming。SyncStateはStreetかつ非Menuだけを再生対象にし、PauseはAudioSource.Pause/UnPauseで位置を保持。RestartMusicは両Sourceを止めて音楽を先頭から初期化する。得点中の音量比とUI音量はunscaledDeltaTimeで補間し、ミュートはmuteで即時反映。シーン/世界移動でAudioSourceを追加生成しない。

### G3-06 全4世界BGMと歓声

HoopsAudioはSE/音楽/歓声の3 Sourceを一度だけ生成。worldMusic配列はStreetTake1/GymTake1/ArenaTake2/NeonTake1、短いStreetCheer/StreetClearCheerはPCM/DecompressOnLoad。SyncStateが世界とMenu/Pauseへ同期し、RestartMusicは3 Sourceを停止して曲を先頭へ。Resultは実得点時のScoreで通常/クリアを選択し、Streetのみ成功ビープを置換。歓声はSE音量とMuteへ追従する。世界変更でSourceは増やさない。

### G3-07 接触音の選択と重複抑制

HoopsBall.OnCollisionEnterは既存の得点/衝突処理を保持し、音声呼出しにCollider名を追加。HoopsAudio.Impactが床/リング/その他へ分類し、同種75ms以内の通知だけ抑制する。HoopsActorは従来どおり1周期1通知。3種のPCMクリップを既存SE Sourceで再生し、Result(true)はネットとStreetのみ歓声を発火。電子音生成を削除。専用素材がない板/支柱はBallBounceを暫定共用する。


### G3-08 Arena歓声

HoopsAudio.ResultはWorldIndex 0でStreet通常/クリア、2でArenaCheer、それ以外は歓声なし。共通の歓声Sourceを再利用して状態制御を維持する。Arenaは受領1本なので通常/クリアで共用。


### G3-09 歓声の共用

WorldIndex 0/1はStreet通常/クリア、2/3はArenaCheerを選択。既存Source・音量・停止/再開・音源加工をそのまま共用する。
