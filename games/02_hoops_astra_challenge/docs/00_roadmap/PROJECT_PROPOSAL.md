# 企画書｜HOOPS: WORLD TOUR

Astra短時間完成チャレンジ / 版1.0 / 2026-09-20 / 企画精査済み・実装前

## 1. 企画の結論

**既存アセットを活用して、4つのコートを巡る3Dバスケットゲームを先に完成させる。その実際の制作過程をSNSで公開し、後からBlenderでディテールアップ、さらに段階学習教材へ展開する。**

今回はUnity入門授業を順番に作る企画ではない。Takaがディレクター兼テスターとなり、ローカルで利用できるAstra/Codexに実装・アセット統合・検証を任せる短時間制作チャレンジである。完成時刻や必要リセット回数を保証する企画でもない。

初版のゲーム形式は、プレイヤーが攻め、CPUが守る「Offensive Challenge」。対戦相手の存在による駆け引きは残すが、CPUの攻撃、攻守交代、リバウンド争奪を省いて完成範囲を明確にする。SNSでも「完全な1on1」ではなく、この実態に合う名称を使う。

### 目的と成果物

| 目的 | 具体的な成果物 |
|---|---|
| Astraの制作能力を実地で検証 | 実行可能なWindowsビルド、試験記録、介入・費用・工程の記録 |
| SNSで制作と成果を見せる | 実プレイ動画、工程比較、使用素材とAIの役割の説明 |
| 既存教材を発展させる | 完成版から切り出すUnity教材の設計材料 |
| 次の品質向上につなげる | 交換可能な人物・ゴール・看板・環境パーツの構造 |

「AIがすべての3D素材をゼロから生成した」と見せる企画ではない。既存素材の利用、人間の判断、実装したコード、後日のBlender作業を区別して示す。

### 明示された希望と、本書で採る設計判断

Takaの明示的な希望は「短時間で先に完成品」「SNS公開」「4種類の世界」「既存素材を先に活用」「Blenderと教材は後段」である。

一方、攻撃側固定、各コート3本、具体的なキー割当、数値、アセットの優先順位は会話を受けた設計判断である。本書の基準案として採るが、Taka本人が数値まで個別に指定した事実として記録しない。変更は要件・意思決定記録へ理由付きで残す。

## 3. 既存HOOPS 3Dとの関係

既存プロジェクトは `Work/Game/games/01_hoops_3d/`。確認したセッション05には、2v2協調守備、選手データ、ON-FIRE、ゲームバランス調整パネルまでの実装記録がある。[I01]

ただし、この整理作業ではそのゲームを実行していない。また、以前の `game.json` は「Phase 2 公開中」のままであり、紹介用メタデータと新しい制作記録には更新差がある。**資料が存在することと、現行ビルドの動作確認は別**として扱う。[I01][I03]

新規のチャレンジは `02_hoops_astra_challenge/` に分離する。既存のソース、教材フェーズ、ダッシュボード、ポータルは変更しない。共通するのは題材、Green Releaseという遊び、制作判断を記録する文化である。JavaScriptコードを機械的にC#へ移すことは目的にしない。

### 参考事例の扱い

テニス事例は、制作の事前確認、素材統合、編集用スクリプト、実行ビルド、検証証拠の残し方が参考になる。一方、そのREADMEは第三者素材全体への一括ライセンスを付与していない。コピーして別ゲームとして配布できると解釈しない。[I04]

OpenAIの公式ページには、Blenderで作った住宅をUnreal Engine内で歩ける空間へする例がある。しかし、それは今回のPCでUnity自動操作がそのまま使えるという証拠ではない。操作手段、認証、エディター、ビルド支援の実在はG0で確認する。[S01]

## 4. 作品の核

「守備を外す → タイミングを合わせる → シュートが入る → 世界が変わる」を短いゲームサイクルにする。

見せ場は、人物の自然な動き、ボールが手を離れる瞬間、リング通過時の音と反応、各世界の印象差。多数の機能より、この一連の体験の整合性を優先する。

初版は1名の攻撃プレイヤーと1名の守備CPU。同一の既存モデルでも配色で区別できればよい。実在選手の名前、チームロゴ、既存リーグを想起させる宣伝表現は持ち込まず、独自の人物・配色を使う。

## 5. 4ワールドのアート方針

| 世界 | 画面を見て分かる特徴 | 主な構成 | 後日の独自化 |
|---|---|---|---|
| Street | 屋外、夕方、街並み、フェンス | 都市の既存CC0パーツ＋共通コート | 独自グラフィティ風サイン |
| Gym | 木床、高い天井、梁、窓 | 簡易体育館シェル＋取得済み床素材 | 学校ロゴ、スコアボード |
| Arena | 大きな客席、暗い外周、中央照明 | 反復式客席・トラス・スクリーン | センタービジョン |
| Neon | 暗色の空間、発光ライン、SFパーツ | 既存SFキット＋発光素材 | ホログラム風ゴール |

見た目はスタイライズド・アーケード寄りに統一。物理コートの寸法、人物の縮尺、UI、ボール、得点判定は4世界で共通とする。背景変更は物理やプレイ領域の変更と切り離す。

初版の「ワールド移動」は、クリア後のカード表示とフェードによる環境切替。歩いてポータルへ入るハブワールドやシームレスなオープンワールドは別の追加目標とする。

### アセットを使う順序

第一候補は公式配布元のCC0素材。人型はQuaternius、環境はQuaternius/Kenney、質感はPoly Havenを中心にする。具体的な無料版のファイル範囲は取得時に確認する。[S05–S10]

Starter Assetsなどの無料Store製品は、有用であっても「無料だからAstra入力も素材再配布も自由」とは扱わない。独自EULA、一般規約、プロジェクトに含める方法が確認できた時だけ採用する。[S03][S04]

既存素材で不足するバスケ用の手の動きやゴールの衝突形状は、小さなUnity側の実装で補う。Hunyuan、TRELLIS、ComfyUI等の新規環境構築は初版のクリティカルパスから外す。

## 6. 完成の段階とチャレンジ運用

| ゲート | 保存する成果 | 判定 |
|---|---|---|
| G0 環境成立 | 空のWindowsアプリ、実行・操作経路の記録 | 開発できる状態。作品完成ではない |
| G1 遊び成立 | 1コートで移動・守備・シュート・3本成功・再開 | 内部チェックポイント |
| G2 見せられる1コート | 人型、基本アニメ、音、演出を含むStreet | 中間公開候補。4ワールド完成とは呼ばない |
| G3 初版完成 | 4世界を通し、結果画面・再プレイまで動くビルド | v0.1の基本完成ライン |
| G4 公開準備完了 | 受入試験、素材台帳、実プレイ動画、公開用ZIP | 人間が確認してSNS投稿・配布を判断 |

リセット前後で必ず工程を分けることはしない。「Playableを先に、その後にPolish」は優先順位として残す。利用枠が途中で切れても、HANDOFFと最新の合格ビルドから続けられる設計にする。

計測は準備、実装、ビルド待ち、素材取得、撮影・編集を分ける。事前調査やダウンロードを含めるかは開始前にログへ記載する。総経過時間、実作業時間、リセット回数、追加費用を混同しない。[S02]

### 費用方針

素材購入、生成API、クラウドGPU、Unity AI有料機能の追加支出は初期予算0円。既存AI契約や適格なUnityライセンスを利用する。Unity Personalは利用資格があるので、個人制作か事業・委託制作かも含めて着手時に確認する。[S11]

有料購入が必要なら、その処理だけ止めて無料の代替を使う。支払いや追加リセット購入を自律実行しない。

## 7. 公開後の発展

第一段階は既存アセットで実プレイできる作品。第二段階ではBlenderで人物、ボール、ゴール、世界ごとの象徴物を改善する。第三段階で実際の履歴から学習可能な順序を組み直し、Unity教材を作る。

教材の再構成順と実際の制作順は区別する。「最初からこの順に進めれば成功した」という架空の開発物語を作らない。失敗、判断、人間の介入、AIの寄与を残すことが、この企画の再利用価値になる。
