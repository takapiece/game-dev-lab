# SNS公開・計測・後日の教材化

版1.0 / 2026-09-20 / 投稿実行はこの文書作成の範囲外

## 1. 企画の見せ方

仮の訴求は「既存の無料素材を使い、Astraと4つのコートを巡る3Dバスケを作る」。成果だけでなく、制限枠を意識した設計、素材統合、失敗と修正、人間が判断した箇所を見せる。

避ける表現は「素材も全部AIが生成」「一発で完全自律」「ゼロ円」「完全な1on1」「数時間で完成」といった未確認の断定。実際に成し遂げた範囲を根拠とともに示す。既存契約料と追加支出0円は違う。

## 2. 計測の境界

開始前にログで以下を固定する。

- 準備：今回の企画・調査、素材の事前取得、Unityのインストール等を含める範囲。
- 本制作：開始プロンプトから公開候補ビルドの確定まで。実作業とビルド・取得待ちは別集計。
- 公開制作：録画、編集、字幕、投稿準備。
- 利用状況：モデル名、設定、確認できた残枠、リセット実施時刻・回数、追加費用。画面を外部へ出す際はアカウント情報を隠す。

リセット回数は完成を保証する契約ではない。期限や提供条件はSettings→Usageで本人確認し、必要な時に操作する。枠を使い切ることより、動くビルドと再開可能な記録を優先する。

## 3. 録画ショット案

| 結果 | 完成状態、実測値、使用素材、人間の役割 | 数字がなければ無理に入れない |

横16:9のゲーム録画を原本とし、SNS用の縦9:16版は編集段階の別出力にする。中央を切るとUIやゴールが欠ける場合は、横画面を余白に収める。無理にゲーム自体の縦画面対応を初版へ追加しない。

短いダイジェストとは別に、開始から終了までの通しプレイを一本保存する。タイトルに使ったモデル名、追加費用、工程時間は記録と一致させる。無関係な通知、氏名、認証情報、第三者の未許諾音楽が映らないよう確認する。

## 4. 公開するもの・しないもの

まず実プレイ動画と制作説明を公開候補にする。Windowsビルドの配布先、公開日、SNSアカウントは未決定。こちらで投稿・共有設定変更をしない。

ソースは自作部分と再配布許可がある素材だけを抽出する。Store素材等が混在する作業プロジェクトをそのまま公開しない。生成・取得・編集済みという事実だけで素材条件は変わらない。

署名なしビルドならその旨と既知制限を伝える。OSの保護を切ることを配布手順にしない。ゲームはローカル完結を基本にし、初版にユーザー行動送信やオンライン接続を足さない。

## 5. Blenderの第2パス

完成版を見て、既製品感や動作の弱さが強い部分から修正する。優先候補は手と球の接点、人物の衣装・配色、リング・ボール、サイン、各世界の象徴物。新しいメッシュを入れても元の衝突・得点・縮尺を壊さない。

変更前後を同一カメラ・同一設定で撮り、見た目の差だけでなく負荷や視認性の変化も比較する。全面作り直しを目標にせず、プレイ体験に効く箇所へ絞る。

## 6. 教材への分解

実際の完成版とログを元に、学習用の順番を再設計する。例として、コート・球、物理と得点、入力、人物・アニメ、守備、世界切替、音とカメラ、検証と公開に分ける。

各単元は、導入前後の実行可能な状態、変更箇所、考え方、試す課題、起こりやすい失敗をセットにする。Sceneだけでなく対応するコードとパッケージ版を固定する。教材用に再構成した順序と実開発の順序を明記する。

後日の `03_hoops_unity_course/` は構想であり、今回は作成していない。既存Web教材にも、このチャレンジにも同じ仕様を二重記入せず、教材化する段階で必要な版を参照する。
